## What we're building

A three-part demo proving out one product concept: a cross-service streaming
discovery app for Fire TV, paired with a phone app that lets a parent set
content limits per child and get real-time alerts when a kid taps something
outside those limits.

**Important scope note for this demo:** the real target platform is Amazon's
Vega OS (Fire TV's new React-Native-based OS), which requires Amazon's own
SDK and native tooling that can't run in this environment. So build the "TV
app" as a **web app styled and navigated like a TV interface** — full-screen,
large focus-highlighted tiles, arrow-key navigation instead of touch/mouse
clicks, remote-control-style UX. This proves the product logic and AI layer
completely; the TV-specific UI would get ported into a real Vega React
Native project later.

## Architecture (3 pieces + shared backend)

```
/backend        - Node.js + Express + WebSocket server (the hub — nothing
                   talks TV-to-phone directly, everything routes through here)
/tv-app         - React web app, styled as a 10-foot TV UI, keyboard-nav only
/mobile-app     - React web app, styled as a mobile phone UI (max-width
                   ~420px container so it visually reads as a phone even in
                   a browser tab)
/shared         - shared types/interfaces used by all three
```

Run all three as separate processes/ports in the same Repl. The backend is
the single source of truth; both frontends poll/subscribe to it.

## Backend (`/backend`)

Build with Node.js, Express, and the `ws` WebSocket library.

### Data layer
Use an in-memory store (a few JS objects/Maps) — no real database needed for
this demo. Seed it with:
- 2-3 mock **parent accounts**, each with 1-2 **child profiles**
- Each child profile: `name`, `age`, and per-category thresholds:
  `violence`, `language`, `sexContent`, `substances`, `scaryContent` — each
  set to `none | mild | moderate | severe` (meaning "block anything above
  this level")

### Title/content data
Do NOT try to integrate JustWatch/TMDB scraping for this demo — that's a
separate concern from proving the architecture. Instead:
- Get a **free TMDB API key** (developer.themoviedb.org) and use TMDB's
  official REST API for: search, title, poster, overview/description,
  genres. This is legitimate, free, and simple — one `fetch` call.
- For the "parental content guide" data (the danger-flagging input), TMDB
  doesn't have this, so **hand-write a small mock dataset** — a JSON file
  with 15-20 well-known titles, each with a plain-text content summary
  covering violence/language/sex/substances/scary-content, written the way
  a Parents Guide entry reads (e.g. "One intense fight scene with blood;
  no sexual content; strong language used twice"). This stands in for the
  licensed IMDb Parents Guide / Common Sense Media data we'd integrate for
  real later — label it clearly in a comment as `// MOCK DATA — replace with
  licensed Common Sense Media / IMDb Parents Guide API in production`.

### Gemini integration — the AI verdict layer
- Use the `@google/generative-ai` npm package.
- Store the API key in Replit Secrets as `GEMINI_API_KEY` — never hardcode it.
- Build one function: `getContentVerdict(title, mockContentGuideEntry, childProfile)`
  that sends Gemini a prompt like:

  ```
  You are a parental content advisor. Given this content guide data for
  "{title}": "{mockContentGuideEntry}", and a child profile of age {age}
  with these thresholds: {thresholds}, respond ONLY with JSON:
  {
    "verdict": "approved" | "flagged" | "blocked",
    "reason": "one sentence, plain language",
    "categoriesOfConcern": ["violence", ...]
  }
  ```

- Parse the JSON response (strip markdown fences defensively, per Gemini's
  known habit of wrapping JSON in ```json blocks).
- This is the core "AI reads licensed text and reasons about age-fit" logic
  from our design — make sure it's a clean, isolated function so it's easy
  to swap the mock data source for a real one later.

### Core API endpoints
- `POST /api/pair` — generate a 6-digit pairing code, associate it with a
  parent account, return the code (TV app displays it)
- `POST /api/pair/confirm` — phone app submits the code, links that phone
  session to the same parent account
- `GET /api/search?q=...` — proxies to TMDB, returns title/poster/overview
- `POST /api/select-title` — **the core flow**: TV app calls this when a
  title is tapped, passing `{ titleId, childProfileId }`. Backend:
  1. looks up the mock content-guide entry for that title
  2. calls Gemini for a verdict against that child's thresholds
  3. if `approved` → responds immediately, TV app proceeds to a mock "now
     playing" screen (no real deep link needed for the demo — just show a
     screen saying "Opening on Netflix...")
  4. if `flagged` or `blocked` → pushes a WebSocket event to that parent's
     connected phone session in real time, AND responds to the TV app with
     a "waiting for approval" state
- `POST /api/approve` — phone app calls this after a parent taps
  approve/deny on the alert; backend pushes a WebSocket event back to the
  TV app to unblock or cancel playback
- `GET /api/profiles/:parentId` — return child profiles + thresholds
- `POST /api/profiles/:childId/thresholds` — update thresholds from the
  phone app

### WebSocket events (this is what makes it feel "seamless" and real-time)
- Each connected client (TV or phone) registers with its `parentAccountId`
  after pairing
- Server keeps a `Map<parentAccountId, Set<WebSocket>>` of connections
- Events to broadcast within that parent's group:
  - `title_flagged` → phone gets a real-time alert with title, verdict
    reason, and approve/deny buttons
  - `parent_decision` → TV gets told to proceed or cancel
  - `thresholds_updated` → so if the TV app shows current settings anywhere,
    it stays in sync

## TV app (`/tv-app`)

React web app. Build it to actually feel like a TV interface:
- Full-bleed dark background, large poster tiles in a horizontal-scrolling
  row layout (like Netflix's home screen)
- **Keyboard navigation only** — arrow keys move focus between tiles
  (highlight the focused tile with a scale-up + border glow), Enter selects.
  Do not rely on mouse clicks/hover as the primary interaction — this is
  the single most important "feels like a real TV app" detail.
- Screens needed:
  1. **Pairing screen** — shown on first launch, displays the 6-digit code
     from `/api/pair`, polls for confirmation
  2. **Child selector** — pick which child profile is "watching" (stands in
     for a real device knowing who's holding the remote)
  3. **Home/search screen** — search bar (focusable, opens a simple on-screen
     keyboard or just a text input for demo purposes), results as tiles
     pulled from `/api/search`
  4. **Title detail screen** — poster, description, a "Play" button
  5. **Waiting screen** — shown after tapping Play if the verdict is
     `flagged`/`blocked`: "Waiting for parent approval..." with a spinner,
     listening on the WebSocket for the parent's decision
  6. **Mock playback screen** — just a full-screen message "Now playing:
     {title} on {service}" — no real video needed

## Mobile app (`/mobile-app`)

React web app, styled in a phone-sized container.
- Screens needed:
  1. **Login/pairing** — parent enters the 6-digit code shown on the TV
  2. **Child profiles list** — tap into a child to edit thresholds (simple
     dropdowns per category: none/mild/moderate/severe)
  3. **Live alert screen** — this is the money screen. When a `title_flagged`
     WebSocket event arrives, show an immediate in-app banner/modal (and
     since this is a browser demo, also trigger a `Notification` browser
     API popup if permitted) with: title, poster, Gemini's plain-language
     reason, and Approve/Deny buttons
  4. **History log** (optional, nice to have) — list of past decisions

## What "done" looks like for this demo
1. Launch backend, tv-app, and mobile-app together (use a root `package.json`
   with a `concurrently` script, or Replit's multi-run config)
2. Pair the phone to the TV using the 6-digit code
3. On the TV, pick a child profile, search a title, hit Play
4. If the mock content data + that child's thresholds trigger a flag: the
   phone gets a real-time alert within ~1 second, parent taps Approve, and
   the TV screen unblocks and shows the mock playback screen — all without
   a page refresh anywhere
5. Confirm the reverse case too: a clean/appropriate title plays instantly
   on the TV with no phone interruption at all
